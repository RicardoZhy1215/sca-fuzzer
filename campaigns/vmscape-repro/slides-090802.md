# violation-260817-090802

## A fault-driven transient cross-actor L1D leak on AMD Zen4

Revizor (side-channel-fuzzer) · guest-user → guest-kernel · contract `ct-ni`
Ryzen 7 8700F (fam 0x19 / model 0x75) · found on ucode 0206, re-tested on 0208

---

# The setup

- **Actors** (config `config-refuzz-u2k.yaml`):
  - `main` — host, kernel
  - `vmvictim` — guest, **kernel** (holds the secret)
  - `vm` — guest, **user**, `observer:true`, `data_properties: writable:false` (attacker / measures)
- **Contract**: observation `ct-ni` (observer must not learn the victim's data) + execution `DEH` (delayed-exception handling)
- **Executor**: `F+R` (Flush+Reload), `x86_enable_hpa_gpa_collisions: true`, threshold `0.5`
- **Template**: `fuzz-multiactor.asm` — victim "secret injection", observer "secret retrieval", both `random_instructions` (fuzzed)

Found by a random-seed refuzz campaign; minimized 236 → **70 instrs**; reproduces **10/10**.

---

# What Revizor flags as a violation

A **counterexample**: two inputs (#34 vs #84) with the **same contract trace** but a **different hardware trace**.

```
================================ Violations detected ==========================
                             HTrace                       | ID:84 | ID:184|
^.^.........^............^................................ | 487   | 0     |   -> lines {0,2,12,25}
^.^......................^................................ | 0     | 487   |   -> lines {0,2,   25}
```

- Same `ct-ni` trace ⇒ per the contract, the observer should see **nothing** of the victim.
- Different htrace ⇒ the hardware leaks it. **Exactly one bit differs: cache line 12.**

---

# The htrace, decoded

HTrace = 64 positions, one per **cache line** of the observer's F+R probe page (`r14+0x000..0xFFF`).

| lines | source |
|---|---|
| 0, 2, 25 | observer's **architectural** accesses (identical for both inputs) — *not* the leak |
| **12** (offset 0x300) | present for #84, absent for #184 — a **speculative** access → **the leak (1 bit)** |

- Common lines map to real instructions (line 25 = `0x9646`, line 2 = `0x909a`).
- Line 12 matches **no** architectural annotation ⇒ it is created **transiently**.

---

# The gadget: sender → receiver

```
main_0 → vm_0   : measurement_start  (FLUSH the 64-line probe buffer)
main_1 → vmvictim_0 : "secret injection"   ← SENDER (architectural)
main_2 → vm_1   : "secret retrieval"        ← RECEIVER (speculative)
                  measurement_end   (RELOAD the 64 lines)
```

- **Sender** = the victim: a single **secret-dependent** memory access.
- **Receiver** = the observer: a fault opens a transient window that re-encodes the secret.
- Only the receiver's *transient* behavior — not its architectural accesses — carries the bit.

---

# Why it is a *violation* (contract vs hardware)

- `ct-ni` says: the observer's observation must be **independent** of the victim's data.
- So the two inputs (differ only in a **victim** byte) have the **same** ctrace.
- The hardware, however, lets the observer distinguish them (line 12) → **the observer learned the victim's secret** → `ct-ni` violated.

The *only* architecturally-differing access is the victim's — the observer's are identical:

```
victim  L61  add [r14+rsi]   [34] 0x697c (line 37) | [84] 0x61eb (line 7)   ← DIFFERS
observer  all accesses        identical across #34/#84
```

---

# The leakage principle (mechanism)

A **fault-driven transient side channel**:

```
victim byte @ 0x640 ─► victim's secret-dependent access (L61) ─► caches victim line 37/7
                                                                          │
observer store to READ-ONLY page (L101, 0xab82) ─► #PF ───────────────────┘
   └─ transient shadow of the fault:
        L104  mov ebx,[r14+rsi]    (transient LOAD: reads the aliased victim value)
        L106  setns [r14+rbx]      (transient STORE: addr = value & 0x1fff → probe line 12)
   └─ L117 lfence closes the window
observer measurement_end (RELOAD) ─► line 12 hot? ─► 1 bit of the victim's secret
```

Trigger = the **write-protection fault**; readout = **younger loads in the fault shadow**.

---

# What value leaks

- Differential input minimizer: **Leaked 1 byte**, address **`0x4640`**.
- Decoded: `0x4640 = actor 1 (vmvictim) · MAIN region · offset 0x640` → **the guest victim's memory byte**.
- That byte selects the victim's access address (line 37 vs 7); the observer recovers **1 bit** of it as probe **line 12** present/absent.

> The **source is the victim** (the observer's input bytes are *identical* across the counterexample, yet the htrace flips ⇒ the varying info can only be the victim's).

# Is it TSA-L1D? — No.

> ⚠️ **SUPERSEDED (Aug 2026).** Later verification overturns this call — see the **UPDATE** section. The three "signatures" below were mis-read, and the 0208-survival is a harness artifact (the executor never issues VERW between actors).

AMD's TSA description gives three signatures; **ours fails all three**:

| AMD TSA | Ours |
|---|---|
| false completion → **no pipeline flush** | a **#PF** (permission flip proves it) → flush |
| consuming ops **don't update cache/TLB**; not F+R-observable | `setns` **encodes a cache line** → read by **F+R** |
| leaks via **timing of other instructions** | leaks via **which cache line** is hot (address channel) |

And empirically: under 0208 the **`tsa: Mitigation: Clear CPU buffers`** is active, yet the leak persists. VERW flushes buffers, not L1D — so it can't stop an L1D-resident channel.

---

# Conclusion

> ⚠️ **SUPERSEDED (Aug 2026)** — see the **UPDATE** section. Correct position: **strongly indicated AMD TSA-L1 microtag false-completion**, a known/already-mitigated attack. The mechanism below (fault-driven transient L1D value-forward) is still accurate; only the "Not TSA" attribution was wrong.

> **A fault-driven transient cross-actor L1D leak**: a store to a read-only page (#PF) opens a speculative window; a younger load reads a victim value and a younger store encodes it into a cache line read out by Flush+Reload — leaking **1 bit** of the guest victim's memory (byte @ 0x640).

- ~~**Not TSA / vmscape / spectre-v2**~~ → **this IS TSA-L1** (microtag). See UPDATE.
- **Survives ucode 0208 in-harness** — *because* the executor's AMD `uarch_flush` is a stub (no VERW between actors), not because the CPU is unmitigated.
- **Does not need the manufactured `hpa_gpa` aliasing** — VA-keyed (microtag), carries over shared L1D sets.

# UPDATE (Aug 2026)

## Re-analysis overturns "Not TSA" → **strongly indicated AMD TSA-L1**

Linear-address **microtag false-completion** — a known, already-disclosed and **mitigated** attack (CVE-2024-36350 · amd-sb-7029), **not** a novel leak.
The gadget mechanism from the earlier slides stays correct; only the *attribution* changes.

---

# Why the original "Not TSA" was wrong

| Original claim | Correction |
|---|---|
| "#PF ⇒ pipeline flush, so not a false-completion" | The #PF is the **trigger** that opens the transient window; the microtag **false-completion** is the leak *inside* the shadow — not mutually exclusive |
| "encodes a cache line ⇒ not F+R-observable like TSA" | Mis-read: TSA-L1 forwards **L1D data**; any transient consumer re-encodes it into a line — that IS the read-out |
| "leaks an address, not timing" | TSA-L1 leaks a **value**, which is then encoded as an address — same thing |
| "survives 0208 + `tsa: Mitigation` ⇒ not TSA" | Executor's AMD `uarch_flush` is a **stub** (`wbinvd; lfence; // TBD`) — **no VERW between actors**, so the mitigation is never applied. Survival = harness bypassing VERW, **not** evidence against TSA |

---

# The re-characterization: VA-keyed → microtag

Decisive test — **`hpa_gpa` OFF** (separate per-actor physical):

- Still leaks, **same byte** (vmvictim / 0x640), with **separate physical pages**
- ⇒ keyed on the **virtual address**, not physical → the AMD L1D **microtag** (a hash of the linear address)

Ruled OUT by A/B tests:

- **Physical aliasing** — off, still leaks
- **SSB** — SSBD forced on, survives 7/7
- **Architectural Take-A-Way µTag** — collide+probe = uniform L1-hit ⇒ Zen4 fixed the *architectural* collision, **not** the *transient* false-completion

---

# Matches AMD's TSA-L1 description

> *"a load may find a valid entry in the **microtag** even though the L1 does not actually contain the data for that load … the invalid data comes from the L1 entry associated with the **matching microtag**."*

| AMD TSA-L1 | Ours |
|---|---|
| matching **microtag** | same VA (both guests at GVA 0x0) ✓ |
| L1 lacks the data for that load | observer's own line absent (separate physical) ✓ |
| forwards the microtag-matching entry | the **victim's** line → its value ✓ |
| cross-context | guest → guest ✓ |

# Corroboration: violation-260825-040842

Found with the repo's **stock** both-kernel config (demo/tsa-l1d style) — a **purer** instance:

- Both actors **kernel**; leaked byte = **vmvictim / 0xb08**
- **No architectural access differs** between the two inputs — a *pure* value-forward
- Reproduces with **`hpa_gpa` OFF** → same VA/microtag path as 090802
- Leaking load pinned by dataflow: **`add edi, [r14+rdi]`**, `rdi & 0x1fff = 0xb0b` → **cache line 44** (the victim's secret line); `rbx→0x1552` cross-checks the fault address

---

# Aligns with "Enter, Exit, Page Fault, Leak" (S&P '26)

The paper's **V2V** (VM→VM) cache leak *is* this mechanism — their words:

> *"the cache contains a value from a victim VM with the **same virtual address (but different host physical address)**."*

- **V2V** (both guests at GVA 0x0 → microtag collides) → **leaks** = our u2k / 040842
- **H2V** (host at vmalloc VA vs guest at GVA 0x0 → no shared VA) → **clean on Zen4**; our `gk2hk` fuzz reproduced this: **V:0 in 40 699 TCs**
- AMD isn't Foreshadow/L1TF-affected ⇒ physical aliasing alone opens no host↔guest path — confirming the leak is **VA-keyed**

---

# Honest caveats — indicated, not mechanism-*confirmed*

- **The VERW A/B is void.** VERW at the observer top closes it 10/10→0/10 on 0208 — **but also** on 0206 (9/10→0/10). The microtag-clear is 0208-gated, so closing on 0206 means VERW isn't acting as that clear. And a **plain `mov rax,[r14]`** closes it too ⇒ VERW's effect was the **incidental memory access**, not a clear. VERW proves nothing here.
- **The one clean fingerprint is untested:** TSA-L1 does **not** leak across **SMT siblings** (microtag isn't SMT-shared). Revizor runs victim + observer on **one thread**, so it cannot test SMT isolation → confirmation needs a **standalone bare-metal PoC**.

---

# Corrected conclusion

> **Strongly indicated AMD TSA-L1** (linear-address **microtag false-completion**): the observer's #PF opens a transient window; a younger load **false-completes on a matching microtag** with the victim's L1D line and forwards its value, encoded via Flush+Reload.

- **VA-keyed**, not physical — survives `hpa_gpa` off; matches the AMD text and the S&P '26 **V2V** finding
- **Survives 0208 in-harness only** because the executor never issues VERW between actors (stub `uarch_flush`); on a real box VERW-on-transition closes it
- **Almost certainly not novel** — matches the already-disclosed / mitigated TSA-L1 — so **no new disclosure**
- **Remaining work:** the **SMT-sibling PoC** — the single decisive test the sequential harness can't run

---

# Open questions / caveats

- **Same-VA layout** (`GUEST_V_MEMORY_START=0x0`) is always on — it *aligns* the L1D microtags; a real attacker relies on microtag **collision** (VA-hash), which is realistic across contexts.
- **Prior-art — RESOLVED:** matches AMD **TSA-L1** microtag false-completion (CVE-2024-36350 · amd-sb-7029) and the S&P '26 **V2V** finding — a known, mitigated class. See the UPDATE section.
- **Real boundary** — the leak is guest↔guest (**V2V**); host↔guest (**H2V**) is clean on Zen4 (no shared VA), as our `gk2hk` V:0 confirms.
- **Bandwidth** — ~1 bit, deterministic; weaker (4/5) with aliasing off.

**Next:** the **SMT-sibling PoC** (the one untested TSA-L1 fingerprint) — a standalone bare-metal check that the leak does **not** cross SMT threads. No disclosure needed (already mitigated).
