# VMSCAPE Reproduction on AMD Zen 4 via Revizor

Automated, differential reproduction of the VMSCAPE (S&P 2026)
core finding: cross-VM indirect-branch predictor residue that IBPB
does not eliminate. Implemented as a series of Revizor `tfuzz`
template variants whose violation rates differentially attribute
the leak to its mechanism.

## Test Platform

| Component | Value |
|---|---|
| CPU | AMD Ryzen 7 8700F 8-Core (Zen 4) |
| vendor_id | AuthenticAMD |
| microcode | `0xa705206` |
| SMT | off (`/sys/devices/system/cpu/smt/active = 0`) |
| spectre_v2 | "Vulnerable; IBPB: disabled; STIBP: disabled" |
| BPB features advertised | `ibpb, ibrs, ssbd, stibp` (no `sbpb`) |
| Tool | Revizor `tfuzz` (multi-actor, F+R executor) |

## Threat Model and Setup

Three Revizor actors:

- `main` (host kernel) — orchestrates VM-enter / VM-exit
- `vmvictim` (guest kernel) — runs first, may train predictor state
- `vm` (guest kernel, `observer: true`, read-only data) — runs second,
  measures cache state

Contract: `ct-ni` (constant-time non-interference, observation only of
architectural memory accesses).  Fast-path model disabled to retain weak
cross-domain signals.  Analyser threshold 0.2.  Sample sizes
`[80, 320, 640, 1280]`.

A test case enters `vmvictim`, runs a victim gadget that ends in
`lea r, [rip + L]; jmp r`, exits to host (no IBPB), enters `vm`,
which loads input bytes and likewise ends in `lea r, [rip + L]; jmp r`.
The `ct-ni` contract requires all input pairs with identical
architectural memory-access patterns to produce indistinguishable
hardware traces.

## Differential Experimental Matrix

Each row is an independent campaign of 10 000 test cases × 50 inputs
generated by `vm.sh <mode>` against the listed template.

| # | Mode (`vm.sh ...`) | Template change vs baseline | Violations | Bugs (arch-mismatch) | Earliest detection |
|---|---|---|---:|---:|---|
| 1 | `fuzz` (baseline) | — | 2 | 0 | TC 1113 |
| 2 | `control` | + IBPB (WRMSR `PRED_CMD=1`) between victim exit and observer entry | 1 | 0 | TC 1279 |
| 3 | `pc-misaligned` | observer's pre-amble grown 16 → 32 random insns → `jmp` PC shifts | 1 | 0 | TC 455 |
| 4 | `no-jmp` | both indirect `jmp`s removed, fall-through to gadget bodies | **0** | 0 | — |
| 5 | `no-victim-jmp` | only victim's `jmp` removed | 0 (at 60 % stop) | 0 | — |
| 6 | `history-perturb` | + 32 deterministic-taken `jz` chain in observer | 1 | **1** | invalid — see note |
| 7 | `trivial-victim` | victim's `function_vmvictim_1` body emptied (just `lfence` + `switch_g2h`) | **0** | 0 | — |

**Note on row 6**: the 32-branch perturbation reliably triggers an
architectural mismatch between Unicorn (the contract model) and the
real CPU.  Revizor saved one such case into `bugs/`; the surviving
"violation" is therefore not trustworthy and is excluded from
conclusions.  See `out-history-perturb/bugs/`.

## What the matrix proves

Reading the matrix as a series of necessity tests:

| Hypothesis | Falsified by | Conclusion |
|---|---|---|
| Cross-VM BTB residue cleared by IBPB | (2) IBPB still leaks | IBPB is **not sufficient** on Zen 4 |
| PC-indexed predictor sharing | (3) misaligned PCs still leak | PC alignment is **not required** |
| Either-side indirect `jmp` alone | (4) no leak with no `jmp`s | Some indirect `jmp` is necessary |
| Observer-only indirect `jmp` | (5) no leak without victim's `jmp` | Both sides must execute an indirect `jmp` |
| Indirect `jmp` is the only thing needed | (7) no leak with trivial victim gadget | Victim gadget **content** is required |

Together these say: the leak channel is

> *victim's `jmp` trains a cross-VM-visible indirect-branch
> predictor entry → observer's `jmp` mispredicts to victim's gadget
> address → observer transiently executes victim's secret-dependent
> code → cache footprint imprints the secret → F+R measurement
> reveals it*.

This is the channel VMSCAPE describes, and it is **not blocked by
IBPB** on this Zen 4 microcode.  Per the paper's Table II, IBPB
on AMD does not cover all relevant predictor sub-structures
(ITA / BHB depending on microcode).

## Known limitations

1. **history-perturb (row 6) is contaminated.** The Unicorn model
   diverges architecturally from the executor on the 32-branch
   perturbation.  A 4-branch variant (`history-perturb-mini`) is
   prepared to revisit the global-branch-history question.
2. **`no-victim-jmp` was stopped at ~60 %** for time.  No violations
   in 6000+ TC.  Should be run to completion for a definitive zero.
3. The `analyser_stat_threshold` was tuned (0.5 → 0.2) during early
   exploration.  Final results in the table use 0.2 throughout.
4. SMT was on for the very first runs; the table above reflects the
   SMT-off configuration that produced the surviving violations.
5. WRMSR-based IBPB in row 2 assumes the kernel-mode test case can
   issue `wrmsr PRED_CMD, 1`.  We did not directly verify that the
   barrier actually retired; we infer it from the lack of effect on
   the violation rate (consistent with VMSCAPE Table II's claim that
   IBPB is incomplete here).

## Reproduce

```bash
sudo bash -c 'echo off > /sys/devices/system/cpu/smt/control'
cd /home/mluo/attack_seq_gen/side-channel-fuzzer
bash vm.sh fuzz            # ~1100 TC to first violation, ~16 min
bash vm.sh control         # IBPB control
bash vm.sh pc-misaligned
bash vm.sh no-jmp
bash vm.sh no-victim-jmp
bash vm.sh trivial-victim
# bash vm.sh history-perturb-mini   # to revisit history channel cleanly
```

To minimize a violation:

```bash
bash vm.sh minimize ./campaigns/vmscape-repro/out/violation-YYMMDD-HHMMSS
```
